ゲート：

定義そのものもチームが PaoBub の中で作ります。進め方の工程で企画リーダーがマインドマップで「新規事業を決めるまでに何が要るか」を広げ、作業役が定義の JSON にし、財務と法務がゲートの条件を足します。途中で定義を 1.0 → 1.1 に上げる場面もわざと入れます。上の表は、できあがる定義の見込みです。open-workflow-definitions へは、PaoBub の中で承認した版を PR にして入れます（下の「道具と定義も PaoBub の中で作る」）。

## 道具と定義も PaoBub の中で作る（2026-11-21 決定）

Ryo さんの決定（カード「両方とも PaoBub の中で作る」）により、マインドマップのエディタ（E1・E2）と工程定義を、私が各リポジトリに直接作るのではなく、PaoBub の Project の中でチームと作業役が作ります。ほかの道具（E3〜E7）も同じ扱いです。

今回は、**open-editor-template から作った Editor を PaoBub に取り込むデモ**も兼ねます（Ryo さん、2026-11-21）。マインドマップのエディタは Open Editor Platform の中の package ではなく、テンプレートから作った別のリポジトリの外部 Editor にし、ビルドした package を PaoBub の外部 Editor の経路で登録して使います。

| Project | 定義 | 作るもの | 外へ出すもの |
| --- | --- | --- | --- |
| A 道具づくり（東雲物産 事業企画部＋DX 推進の開発担当） | software-product（既存）。工程は進め方〜手元で作る（build-local）まで。dev・staging・release は省き、理由を書く | open-editor-template から作ったマインドマップのリポジトリで、E1 を作る。ビルドした package（`dist/paobub/`）が出すもの | package を PaoBub に登録（E2）。PaoBub 側に足りない所は paobub の Issue と PR。後の段の道具（E3〜E7）は、Open Editor Platform の拡張か新しい外部 Editor かを段ごとに決める |
| B 新規事業の企画 | 最初は手元だけの小さな定義（進め方の 1 工程）で始め、工程 0 で作った new-business-planning 1.0.0 に定義を上げる | 新規事業計画（工程 1〜12） | 承認した定義の PR（open-workflow-definitions）、最後の記録（このフォルダー） |

- Project A でチームが決めること（範囲・利用者の話・画面・状態・前提・設計）は、作業役が下書きし、人がスレッドで議論して承認します。先に出した設計の下書き（Open Editor Platform #42）と定義の下書き（open-workflow-definitions #14）は、作業役への参考資料として渡すだけにし、PR は下書きに戻しました。
- 道具のコードは、Project A の作業ブランチで作業役が書き、ゲート（テンプレートの `npm run check`・`npm test`・`npm run build`・`npm run verify:package`）を通します。Project A のリポジトリはテンプレートから作った専用のものなので、`workflow.json` などの Project のファイルもそこに置けます。
- 取り込み：運用者（人）が `host-pin.json` を確かめて信頼に登録し、package を置き場へ置き、Project B の `editorBindings` に書きます。生成物の pin をそのまま信頼しないことも、デモで見せます。
- Project B は、定義の更新（小さな定義 → 1.0.0 → 1.1）を最初から通るので、「定義の更新を既存の Project に反映」の確かめにもなります。

## 実行時の Project の分け方

PaoBub は独立したリポジトリを機密の範囲として扱い、同じリポジトリの中のフォルダーやフォルダー型の Subproject では見せる範囲を分けられません。そこで、実行時は 2 つのリポジトリに分けます。

| 実行時の範囲 | 置くもの・共有のしかた |
| --- | --- |
| 東雲物産の親 Project（リポジトリ 1） | 工程 0–4、6–12 の成果物。収支、投資の判断、計画書、スライド、経営会議の記録 |
| 実行計画の Subproject（独立したリポジトリ 2） | 工程 5 の実行の計画（拠点・回収の物流・再製造工場・日程）。提携先の技術担当を招くのはここだけ |
| 両者の受け渡し | 親から Subproject へは、必要な成果物の承認済みの公開版だけを渡す（例：回収量の前提の一部）。Subproject の受け入れ済みの版を親が引く |

このフォルダー（`projects/shinonome-ev-circular/`）は、完成後の記録をまとめて置く場所です。実行時の構成そのものではありません。記録には、Subproject の中身を `subproject-execution/` として分けて入れます。

前回の指摘は「PaoBub ドッグフーディング：使いにくい点といい点」の文書と、その直し（paobub #333）です。各工程では、作業役の下書き → スレッドでの複数人の議論 → 注釈と手での直し → 承認、の流れを収録し、白羽と同じくメイキング動画にします。

## 段取り

1. **B0 計画**：この計画（#8）と、道具・定義を PaoBub の中で作るための直し（この節）。手元の PaoBub を起こし、ペルソナと Project A・B を用意する。
2. **B1 マインドマップ**：Project A で E1 と E2 を作る（進め方〜手元で作る）。できたら Project B を立て、工程 0 でマインドマップから定義を作って承認し、定義を 1.0.0 に上げる。工程 1–2 を回す（G1 まで）。
3. **B2 収支の道具と工場の接続**：E3 と、Factory エディタの PaoBub への接続（E7）。今の PaoBub には `factory` のエディタが入っておらず、`editorBindings` に書くと「Editor の種類 factory はこの道具に入っていません」と拒否されます。Factory 自体は作り直さず、組み込みにするか外部のエディタにするかは B2 の設計で決めます。工程 3–8 を回す（G2 まで）。地図（geo）と日程（schedule）は今の接続を使う。
4. **B3 スライドのアニメーション**：E4。書き出し（MP4・PDF・PPTX）まで。
5. **B4 引用と文書からスライド**：E5 と E6。工程 9–11 を回す（G3 まで）。
6. **B5 仕上げ**：学びの工程、メイキング動画と発表の動画、このフォルダーに Project の中身、使いにくい点のまとめ。

受け入れは 3 回です。

- K1（B1）：Project A でテンプレートから作ったマインドマップのエディタを、package として PaoBub に登録し、Project B の成果物から開いて、編集・保存・再読込ができる。Project B の工程 0 で作った定義が検査を通り、承認されて Project に当たっている。
- K2（B2–B3）：PaoBub の上で、収支の前提を変える → 再計算 → 差分を見る → 採用する → 保存・再読込する、を通す。これに加え、PaoBub の成果物から工場のエディタを開き、編集・保存・再読込ができる。スライドのアニメーションが書き出せる。
- K3（B4–B5）：引用（E5）を含む最終のスライドを MP4・PDF・PPTX に書き出し、形式ごとに保たれるもの（数字・図・引用の元・アニメーション）と失われるものを一覧にして確かめる。今の artifact-references は参照つきの PPTX の出力を拒否し、参照の明示的な解除を求めるので、その扱いを E5 で決める。道具は統合ブランチへの段階 PR で作り、main への受け入れ PR は Ryo さんの「マージして」でだけマージします。PaoBub 側に要る直しは paobub に Issue を立てて進めます。

### U2：収支の道具の初版

財務担当が回収率の仮定を変え、結果を比べて採用し、計画書とスライドへ反映するところまでを、一連の仕事として確かめます。

- **前提表**：値・単位・通貨・出典か仮定か・説明を、変わらない前提 ID（AS-nn）に結ぶ。
- **10 年の年次モデル**：売上、費用、設備投資、資金の動き。
- **3 シナリオ**：基本・楽観・悲観と、主な前提の感応度。
- **投資の指標**：NPV・IRR・回収年。計算の条件と丸めを固定する。
- **根拠と版**：結果から前提に戻れ、過去に受け入れた結果を保つ。
- **通貨**：集計の基準通貨を 1 つ決め（円の予定）、タイバーツとの換算率を明示した前提として持つ。
- 前提と計算結果の版は E3 で決め、スライドへの引用は E5 につなぐ。

### U3：工程定義を作る流れ

1. マインドマップで、要る仕事・成果物・判断を整理する（企画・財務・法務がそれぞれの観点から枝を足す）。
2. 作業役が、工程・成果物・引用の関係・受け入れの条件を定義の JSON にする。
3. 今の検査（open-workflow-definitions の check）を通し、作られた工程を人が読める形で確かめる。
4. 人が承認した版を、Project で使う定義として固定する。
5. 途中の変更は、差分を確かめてから新版として当てる（1.0 → 1.1）。

どの枝の議論がどの工程や受け入れの条件になったかの対応を `trace/definition-from-mindmap.json` に残します。あわせて「JSON を作った後に何を何度直したか」「どの関係がわかりにくかったか」を記録し、定義専用のエディタを作るかどうかの判断材料にします。

### U4：数字の種類

| 数字の種類 | 持つもの |
| --- | --- |
| 公表された実績・統計 | 出典、対象の地域、対象の年、単位 |
| 外部機関の予測 | 出典、予測の条件やシナリオ |
| この企画の仮定 | 仮定であること、理由、想定する幅 |
| 計算結果 | 使った前提と、計算モデルの版 |

- 例：IEA の Global EV Data Explorer の EV の販売・保有台数は、実績と予測を分けて取り込む。
- 回収率、診断後に再利用できる割合、再製造の費用、販売単価などは、この企画の仮定として理由と幅を説明できるようにする。
- 見せ場：財務担当が「この回収率は楽観的ではないか」と指摘し、前提を変えた結果、採算と投資の判断がどう変わるかを確かめる。

### U5：3 つの成果物の役割

- **編集できるスライド**：計画を直し、別の場で説明するための成果物。
- **発表の MP4**：東雲物産の事業案、収支、リスク、投資の判断を通して説明する動画。
- **メイキング動画**：人と作業役が、成果物をどう作り、直し、承認したかを見せる動画。誰が何を判断し、その判断が成果物にどう反映されたかを見せる。優先する場面は次のとおり。
    - マインドマップから事業の仮説を整理する。
    - 財務担当が収支の前提を直し、シナリオを比べる。
    - 法務・リスク担当が差し戻し、その内容を反映する。
    - 提携先と実行計画を共同作業する。
    - 前提の変更で引用が古くなり、説明の資料を更新して承認する。

スライド・MP4・PDF・PPTX は、同じ受け入れ済みの版から書き出します（K3）。

### U6：読み上げと字幕

1. 発表者ノートを、読み上げやすい話し言葉に整える。
2. 最初に 30〜60 秒のサンプルを作り、固有名詞・略語・数字の読みを確かめる。読みは pyopenjtalk のユーザー辞書でそろえる（「東雲物産」「e-Axle」など）。サンプルは Ryo さんに聞いてもらってから先へ進む。
3. 同じ台本から音声と字幕を作り、スライドの切り替えに合わせる。
4. 台本と音声を分けて保ち、後で音声を差し替えられるようにする。

完成の条件は、説明が明快で、数字の読みが正しく、字幕でも追えることです。

## このフォルダーに入るもの（予定）

- `workflow.json`、`definition.json`（new-business-planning）、最初の小さな定義
- `tools-project/`：Project A（道具づくり）の成果物と記録（コードは各リポジトリの PR にある）
- `docs/`：親 Project の成果物（マインドマップ、仮説、市場、事業モデル、収支、リスク、投資の判断、計画書、スライド、承認の記録、学び）
- `subproject-execution/`：実行計画の Subproject の中身（実行の計画、地図、工場、日程）
- `data/`：前提 AS と出典の一覧
- `trace/`：引用と判断の記録、定義の変更の記録、マインドマップの枝と工程の対応（`definition-from-mindmap.json`）
- `narration/`：発表の台本、読みの辞書、字幕（音声と動画は大きいので入れない）
- `assets/`：スライドの静止画（動画は大きいので入れない）
